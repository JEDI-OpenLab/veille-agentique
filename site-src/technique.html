Installation technique

Ce qu’il faut pour monter une équipe comparable sur un serveur Linux : Hermes Agent, Hermes Virtual Office, des clés ILaaS et Albert, un blog Ghost.

Relevé du 24 novembre 2026 sur Ubuntu 22.04, avec Hermes Agent 0.23.2, Virtual Office (version 1d23350) et Ghost 6.63. Les commandes d’installation viennent des documentations de ces projets ; nous n’avons pas refait l’installation de zéro pour écrire cette page.

Hermes Agent

Sur Linux, macOS ou WSL2, la documentation propose un installateur. Comme tout script téléchargé, mieux vaut le lire avant de l’exécuter.

curl -fsSL https://hermes-agent.nousresearch.com/install.sh -o install.sh
less install.sh
bash install.sh

Puis on choisit un fournisseur, on vérifie, et on installe le service qui fait tourner les agents en continu :

hermes model
hermes doctor
hermes gateway install

Créer l’équipe

Chaque agent est un profil, avec ses consignes, son modèle et ses clés.

hermes profile create nestor
hermes profile create jarvis --clone-from nestor
hermes profile list

Les consignes vont dans ~/.hermes/profiles/<profil>/SOUL.md. Les nôtres sont dans le dépôt.

Les clés ILaaS et Albert

Une clé API identifie celui qui appelle un modèle. C’est un secret, au même titre qu’un mot de passe.

ILaaSAlbert API
Qui le porteUne fédération d’établissements de l’enseignement supérieur et de la rechercheL’État, via les services de ia.numerique.gouv.fr
Obtenir une cléPasser par la direction du numérique de son établissementDemande d’accès, validation, puis création de la clé dans l’interface. Vérifier d’abord son éligibilité : le service est ouvert aux administrations de l’État et aux organismes sous sa tutelle, même partagée (questions fréquentes)
Adressehttps://llm.ilaas.fr/v1https://albert.api.etalab.gouv.fr/v1

Les conditions d’accès, les quotas et les modèles évoluent : vérifiez-les auprès de chaque service. Albert n’affiche la clé complète qu’à sa création (documentation).

Ranger les clés

Dans le fichier .env du profil, lisible par son seul propriétaire :

ILAAS_API_KEY=votre-cle
ALBERT_API_KEY=votre-cle
chmod 600 ~/.hermes/profiles/nestor/.env

Dans config.yaml, on cite le nom de la variable, jamais la clé :

model:
  default: gemma-4-31b
  provider: custom
  base_url: https://llm.ilaas.fr/v1
  api_key: ${ILAAS_API_KEY}

custom_providers:
  - name: ilaas
    base_url: https://llm.ilaas.fr/v1
    key_env: ILAAS_API_KEY
  - name: albert
    base_url: https://albert.api.etalab.gouv.fr/v1
    key_env: ALBERT_API_KEY

fallback_providers:
  - provider: custom
    model: gemma-4-31b-it
    base_url: https://albert.api.etalab.gouv.fr/v1

Cet exemple est simplifié. hermes model génère ses propres noms de variables. Le nom d’un modèle doit correspondre exactement à celui que le service propose :

curl -s -H "Authorization: Bearer $ILAAS_API_KEY" https://llm.ilaas.fr/v1/models

Le piège du secours silencieux

Qwen, sur ILaaS, refusait le niveau de raisonnement « high » et Hermes passait au modèle de secours. Il faut un réglage propre à ce modèle :

agent:
  reasoning_effort: high
  reasoning_overrides:
    qwen-3.8-27b: medium

Puis lire dans les journaux quel modèle a répondu :

grep -E 'API call|Fallback activated' ~/.hermes/profiles/r2d2/logs/agent.log | tail

Hermes Virtual Office

À savoir avant d’installer : l’interface est en grande partie en indonésien, avec de l’anglais par endroits. Il n’y a pas de version française.

La documentation est en anglais, ce qui peut surprendre ensuite. Dans la version que nous avons relevée, aucun choix de langue : nous n’y avons trouvé ni bibliothèque ni fichier de traduction. Les textes sont écrits directement dans le code.

Nous avons donc traduit l’interface à la main, fichier par fichier. C’est faisable, mais incomplet, et à refaire ou à fusionner à chaque mise à jour. Extraire les textes dans des fichiers de langue serait une belle contribution à proposer au projet.

Installer

Il faut Node.js, et que l’office tourne sur la même machine que Hermes, car il pilote sa ligne de commande.

git clone https://github.com/JuniorXcoder/hermes-virtual-office.git
cd hermes-virtual-office
cp .env.example .env.local
npm install
npm run build
npm start

Dans .env.local, une ligne est obligatoire, avec le chemin complet :

HERMES_BIN=/chemin/vers/hermes

Sans elle, l’interface affiche que le serveur est hors ligne. Nous l’avons appris en relançant l’office sans lui transmettre ce chemin.

Protéger l’accès

  • Laisser l’office sur 127.0.0.1, derrière un serveur web qui demande un mot de passe, en HTTPS.
  • L’interface peut agir sur les agents et supprimer un profil. Nous avons ajouté un filtre qui n’autorise que la lecture ; il n’existe pas dans le projet d’origine.
  • Ne pas l’exposer sur Internet.

Ghost et le circuit

Dans Ghost, créer une intégration personnalisée fournit une clé d’administration. Seul le profil qui publie en a besoin :

GHOST_API_URL=https://votre-blog
GHOST_ADMIN_API_KEY=votre-cle

Placer ensuite les scripts de dispositif/ dans ~/laboratoire-veille, avec sources.md et un fichier deja_vu.txt, même vide. office.py attend Hermes dans ~/hermes-agent : adapter ce chemin si besoin. Copier les deux fichiers systemd dans ~/.config/systemd/user/, puis :

touch ~/laboratoire-veille/deja_vu.txt
systemctl --user daemon-reload
systemctl --user start --no-block office-veille.service
systemctl --user enable --now office-veille.timer

La troisième ligne lance un premier passage, qui peut publier. La dernière active l’horaire. Pour que tout fonctionne sans session ouverte, l’administrateur active loginctl enable-linger pour le compte.

Vérifier avant de faire confiance

  1. Chaque agent répond, et avec le modèle prévu.
  2. Aucune clé dans les consignes, le dépôt ou les captures d’écran.
  3. Le compte des agents n’a pas de droits d’administration.
  4. Profils, dossiers de passage et blog sont sauvegardés.
  5. Le premier billet est lu par un humain.
